# HolyAgent on the operator account

Use **T3 Code + Pi**. Do not substitute standalone Pi or Claude Code as the user interface. This profile does not register providers, grant Full access, enable CUA, publish software or enroll Tailscale.

## Pinned inputs

- **HolyAgent 0.3.3:** fetch the [published npm tarball](https://registry.npmjs.org/holyagent/-/holyagent-0.3.3.tgz). The matching [source tag](https://github.com/davidbasilefilho/holyagent/tree/holyagent-0.3.3) and [registry metadata](https://registry.npmjs.org/holyagent/0.3.3) document its provenance. The overlay verifies the pinned SHA-512 before extracting. **There is no npm `bin` in this release.** The archive does contain `scripts/holyagent`, its Bun-backed wrapper; do not rely on an invented npm global executable.
- **Pi 1.5.0:** use the frozen `apps/agent-host` dependencies. System Node.js must meet the pinned Pi release's minimum (22.19.0). The HolyAgent wrapper also requires Bun in the operator's PATH.
- **T3 Code 0.1.10:** use the verified native Linux x64 archive, not an npm shim that fetches a runtime on first use. Use the build instructions in [agent host tools](../agent-host/README.md). Never put credentials, a live HOME or a paired T3 state directory into an image.

Pass both the prepared tools tree (`--agent-tools`) and the HolyAgent archive (`--holyagent`) to the [overlay builder](../../platform/README.md). The latter is a build input, not vendored in Git. Bundle the compiled t1os CLI with `--cli`. Giving only the HolyAgent archive stages the extension but does not make T3 or Pi runnable. No start is implied by provisioning.

## First boot and activation

First boot runs `stage.py` as the locked-password `t1os` operator, never as root. It registers the verified local package under `~/.pi/agent/settings.json`, points its peer imports at the pinned Pi installation, and enables just the Pi driver in `~/.t3/userdata/settings.json`. It will not rewrite a different existing setting. In that case inspect the files, keep any other settings, and add the equivalent local package path and Pi provider entry yourself. Retry from the guest console. If an installed file differs from its pinned contents, investigate rather than automatically replacing it.

Before activation, check each binary with `--version` from a clean directory as the operator. The bundled HolyAgent wrapper is at `~/.local/share/t1os/agent/holyagent-0.3.3/scripts/holyagent`. The installation does **not** run the upstream interactive setup, fetch feature extensions, enable its storage cleanup, grant access to devices, or authenticate GitHub/model providers. Review the [upstream setup and required feature packs](https://github.com/davidbasilefilho/holyagent/blob/holyagent-0.3.3/docs/pi/installation.md) and enable only what your trusted workload needs after inspecting its settings. A fully configured live thread is an operator acceptance step, not something CI claims to test.

After checking the runtime paths and versions, enable lingering for `t1os` from the guest's admin console. As `t1os`, create `~/.config/t1os/enable-t3` and enable/start the `t1os-t3.service` user unit. It binds 127.0.0.1:3773 and does not add a tailnet route. Use an SSH local forward as described in [remote access](../README.md). Verify the actual listener with `ss -lntp` and use the installed T3 binary's local pairing flow on the guest console. Never put pairing links, bearer tokens, provider keys, or passwords into logs. The unit discards application output because T3 can print pairing credentials; use `systemctl --user status t1os-t3` and the unit journal for lifecycle and exit status. The root-owned managed policy explicitly disables T3 Connect (an outbound relay), telemetry, browser cookie import, webhooks and automatic updates, and limits drivers to Pi. The pinned T3 binary accepted this policy. If the existing machine policy differs, provisioning stops rather than overwriting it. Do not enable hosted pairing, LAN binds, Serve or Funnel.

Use T3's Pi provider only in a trusted workspace. Its agent access does not become sandboxed simply because rootless Podman is available for individual CLI jobs. Security-sensitive and untrusted work belongs in a separate disposable guest. To stop remote access, disable the optional units, remove the activation marker, and revoke relevant pairings/keys using the operator's console. Do not erase T3 userdata, Pi state, worktrees or work-in-progress.
