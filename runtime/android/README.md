# Local Android device profile (opt-in)

Installs a local x86-64 Android 15/API 35 AOSP emulator and configures T3 Code v0.1.10 to use its own private Device Hub. Nothing in this directory runs on an ordinary install. No Android Studio, graphical login, USB passthrough, Google account, SSH device host or cloud device service is needed. This configuration is for a dedicated, trusted, single-operator full guest; the emulator and its state are not a sandbox for hostile APKs.

## Requirements and installation

1. Install the [full t1os guest](../../platform/README.md) first. Nested hardware virtualization must be exposed by the host and readable/writable at `/dev/kvm` by the guest operator. Use an administrator-managed per-user ACL limited to the guest KVM device. Do not add the operator to a supplementary group: t1os verifies its group set during provisioning. Do not use root or world-writable KVM permissions. Nested operation is conditional rather than a supported guarantee for generic VMs: the [Android acceleration guide](https://developer.android.com/studio/run/emulator-acceleration) recommends the physical host; Google's [emulator container examples](https://github.com/google/android-emulator-container-scripts) describe particular nested-KVM environments. Without acceleration this profile fails instead of silently falling back to software CPU emulation. Budget space for several GB of SDK, virtual disk and guest data. In the guest provide Java compatible with the command-line tools, npm, unzip, diffutils, and ffmpeg with libx264. No change to default service permissions is made.
2. Google's [Linux command-line tools download](https://developer.android.com/studio#command-tools) is an operator-supplied input: `commandlinetools-linux-15859902_latest.zip`, SHA-256 `4e4c464f145a7512b57d088ac6c278c03c9eea610886b35a5e0804e74eedf583`. Read the license yourself. In a terminal as the guest's `t1os` operator run the following. A matching existing SDK is reused without running SDK Manager. An incomplete or mismatched SDK is left untouched and must be reviewed manually. For a fresh install the helper stages under a private sibling, verifies the exact revisions, and promotes without overwriting a concurrent installation; SDK Manager may prompt for licenses and downloads only the selected packages. The stock harness has **no network** and cannot fetch these packages or the Hub. Use a separately approved networked guest or independently prepared, verified local SDK and T3 tool cache for an offline installation; do not turn on networking in the installer harness. No SDK or SDK license acceptance is redistributed in t1os.

   ```sh
   t1os android install-sdk /path/to/commandlinetools-linux-15859902_latest.zip
   t1os android check
   systemctl --user stop t1os-t3.service
   t1os android configure
   ```

   The profile requires command-line tools **22.0**, Platform-Tools **37.0.1**, Emulator **37.2.13**, and AOSP x86-64 system image **API 35 revision 2**. The [Google tools catalog](https://dl.google.com/android/repository/repository2-3.xml) and [system image catalog](https://dl.google.com/android/repository/sys-img/android/sys-img2-3.xml) identify the exact artifacts. SDK Manager selects stable packages; if the channel moves, configuration and launch reject mismatched revisions. Retain an authorized, verified local SDK snapshot for exact repeat installs. SDK Manager does not support selecting an arbitrary historical revision of these packages by ID.

3. The operator can now start T3 using the [existing T3 opt-in](../agent/README.md). T3 requests the optional emulator in parallel; chat does not wait for Android or stop if Android fails. The Android unit alone waits for the expected AVD and its boot property. Temporary ADB disconnects are retried within four minutes; a confirmed different AVD fails immediately. Refresh Devices when Android is ready. While requested, systemd restarts an exited emulator after five seconds, up to three starts per 15 minutes; an explicit `systemctl --user stop t1os-android.service` is not restarted (a shutdown from inside Android is an emulator exit and is restarted). Stopping or restarting T3 propagates to the emulator. If Android reaches its start limit, correct the cause, then use `systemctl --user reset-failed t1os-android.service` and `systemctl --user start t1os-android.service` without disrupting chat. Configuration alone does not start either service. Open **Device** in that T3 environment and select the **running** `t1os_api35` device; use the unit, not the panel, to restart a stopped headless AVD. T3 supervises its loopback-only Hub and installs `expo-device-hub@0.22.1` on demand through npm. For the first online use, allow for its own dependency download. Agent control is explicitly **off**; grant it separately in T3 only if desired. Never expose ADB (5037), emulator ports (5554/5555) or the Hub directly. Open T3 at the **localhost end of its private SSH tunnel**, or use an existing authenticated HTTPS endpoint. Local Android video requires a secure browser context and support for H.264 through WebCodecs. A private IP or Tailscale hostname served over plain HTTP does not meet that requirement.

### Manual controls versus HolyAgent/Pi

The Device panel can stream and accept manual input with agent control off. Setup refuses to silently inherit an existing project-level device grant. If the operator explicitly enables **Agents can use devices** and grants access to this project, start a new Pi session. Pi's T3 MCP bridge can discover the session-authorized tools even though this T3 version does not inject the device-use prompt hint into Pi. Discover **device_list**, use **device_open** on the local AVD, and use the bound launcher it returns for input; **device_screenshot** and **device_close** are separate tools. This path does not require switching provider or granting shell access to a remote device host. See the [pinned Pi bridge](https://github.com/pingdotgg/t3code/blob/v0.1.10/packages/provider-pi/src/server/mcpExtensionSource.ts#L395-L450) and [device-open handler](https://github.com/pingdotgg/t3code/blob/v0.1.10/apps/server/src/mcp/toolkits/device/handlers.ts#L244-L310).

## Acceptance and reversal

Check `systemctl --user status t1os-android.service t1os-t3.service` and run `~/Android/Sdk/platform-tools/adb -s emulator-5554 shell getprop sys.boot_completed` (must be `1`). In T3 verify the live frame changes, touch an app, and repeat after restarting the service. This is a preparatory profile, not a report of a successful live run. Neither live UI input nor an agent-driven HolyAgent/Pi session has been verified. An ADB boot check alone does **not** qualify T3 streaming/input or Pi agent control. A TCG-only outer guest or a runner without nested KVM cannot qualify this profile.

To disable: switch **Use devices** off in T3, stop T3, remove only the managed user files `~/.config/systemd/user/t1os-t3.service.d/android.conf` and `~/.config/systemd/user/t1os-android.service`, then run `systemctl --user daemon-reload`. Starting T3 no longer boots Android. SDK, AVD and app data stay on disk. Never delete the operator's entire T3 settings or Android home.
