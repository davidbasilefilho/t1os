# Android and the local T3 Device Hub

The default full guest includes the configured T3 Device Hub and a managed headless Android emulator launcher. No second profile is required. Android binaries and its licensed system image are not redistributed. No Android Studio, graphical login, USB passthrough, Google account or cloud device service is needed. This configuration is for a dedicated, trusted, single-operator full guest; the emulator and its state are not a sandbox for hostile APKs.

## Requirements and installation

1. Install the [full t1os guest](../../platform/README.md) first. Nested hardware virtualization must be exposed by the host and readable/writable at `/dev/kvm` by the guest operator. Use an administrator-managed per-user ACL limited to the guest KVM device. Do not add the operator to a supplementary group: t1os verifies its group set during provisioning. Do not use root or world-writable KVM permissions. Nested operation is conditional rather than a supported guarantee for generic VMs: the [Android acceleration guide](https://developer.android.com/studio/run/emulator-acceleration) recommends the physical host; Google's [emulator container examples](https://github.com/google/android-emulator-container-scripts) describe particular nested-KVM environments. Without acceleration this profile fails instead of silently falling back to software CPU emulation. Budget space for several GB of SDK, virtual disk and guest data. In the guest provide Java compatible with the command-line tools, unzip and ffmpeg with libx264. No change to default service permissions is made.
2. Google's [Linux command-line tools download](https://developer.android.com/studio#command-tools) is an operator-supplied input: `commandlinetools-linux-15859902_latest.zip`, SHA-256 `4e4c464f145a7512b57d088ac6c278c03c9eea610886b35a5e0804e74eedf583`. Read the license yourself. In a terminal as the guest's `t1os` operator run the following. A matching existing SDK is reused without running SDK Manager. An incomplete or mismatched SDK is left untouched and must be reviewed manually. For a fresh install the helper stages under a private sibling, verifies exact revisions and promotes without overwriting a concurrent installation; SDK Manager may prompt for licenses and downloads only the selected packages. The stock harness has **no network** and cannot fetch these packages. Use a separately approved networked guest or independently prepared, verified local SDK for an offline installation; do not turn on networking in the installer harness. No SDK or SDK license acceptance is redistributed in t1os.

   ```sh
   # Skip if an authorized, verified SDK already exists at ~/Android/Sdk.
   t1os android install-sdk /path/to/commandlinetools-linux-15859902_latest.zip
   t1os android check
   t1os android start
   ```

   The profile requires command-line tools **22.0**, Platform-Tools **37.0.1**, Emulator **37.2.13**, and AOSP x86-64 system image **API 35 revision 2**. The [Google tools catalog](https://dl.google.com/android/repository/repository2-3.xml) and [system image catalog](https://dl.google.com/android/repository/sys-img/android/sys-img2-3.xml) identify the exact artifacts. SDK Manager selects stable packages; if the channel moves, configuration and launch reject mismatched revisions. Retain an authorized, verified local SDK snapshot for exact repeat installs. SDK Manager does not support selecting an arbitrary historical revision of these packages by ID.

3. `t1os android start` checks prerequisites, creates or reuses the managed AVD and explicitly starts it. Neither installation nor a T3 start boots Android. A missing SDK or inaccessible KVM does not prevent ordinary chat. Start T3 independently using the [private operator route](../agent/README.md); select the **running** `t1os_api35` under **Device**. Android waits up to four minutes for the expected AVD and its boot property, retrying transient ADB errors but rejecting a confirmed different device. While requested, systemd retries an exited emulator after five seconds, up to three starts per 15 minutes. To release resources, run `systemctl --user stop t1os-android.service`; it stays stopped. If the start limit trips, fix the cause, run `systemctl --user reset-failed t1os-android.service`, then retry.

4. The full guest prepares the pinned `expo-device-hub@0.22.1` helper for T3. The manual Device panel is available by default, not agent control. Never expose ADB (5037), emulator ports (5554/5555), or the Hub directly. View T3 at **localhost through its private SSH tunnel**, or over an already authorized HTTPS endpoint: local Android video needs a secure browser context and H.264 WebCodecs. Plain HTTP over a private address is not a secure context.

### Manual controls versus HolyAgent/Pi

The Device panel can stream and accept manual input with agent control off. First boot never grants agent control; existing operator choices are not overwritten. An upgrade preserves the previous T3 settings file: if it predates Device Hub or explicitly disabled it, turn **Use devices** on in T3 once. If the operator explicitly enables **Agents can use devices** and grants access to this project, start a new Pi session. The separate `agent-device@0.21.36` driver is pre-cached offline in the full profile. Its presence does not grant agent access or launch the daemon. End-to-end agent control is not certified. Pi's T3 MCP bridge can discover the session-authorized tools even though this T3 version does not inject the device-use prompt hint into Pi. Discover **device_list**, use **device_open** on the local AVD, and use the bound launcher it returns for input; **device_screenshot** and **device_close** are separate tools. This path does not require switching provider or granting shell access to a remote device host. See the [pinned Pi bridge](https://github.com/pingdotgg/t3code/blob/v0.1.10/packages/provider-pi/src/server/mcpExtensionSource.ts#L395-L450) and [device-open handler](https://github.com/pingdotgg/t3code/blob/v0.1.10/apps/server/src/mcp/toolkits/device/handlers.ts#L244-L310).

## Acceptance and reversal

Check `systemctl --user status t1os-android.service t1os-t3.service` and run `~/Android/Sdk/platform-tools/adb -s emulator-5554 shell getprop sys.boot_completed` (must be `1`). In T3 verify the live frame changes, touch an app, and repeat after restarting the service. This is a preparatory profile, not a report of a successful live run. Neither live UI input nor an agent-driven HolyAgent/Pi session has been verified. An ADB boot check alone does **not** qualify T3 streaming/input or Pi agent control. A TCG-only outer guest or a runner without nested KVM cannot qualify this profile.

To disable device preview, switch **Use devices** off in T3. To stop Android, stop its user service. Nothing automatically enables it on boot. SDK, AVD and app data stay on disk. Do not remove the machine-managed service definitions.
