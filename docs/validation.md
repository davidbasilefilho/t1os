# Validation and acceptance

The repository's default checks never install an operating system, enroll a tailnet, authenticate a provider, or execute code in a user's worktree.

| Layer                      | Repeatable check                                                                                         | What it establishes                                                                                                                                                 |
| -------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspaces                 | `bun install --frozen-lockfile --ignore-scripts`; `bun run verify`                                       | One frozen lock, format, type-aware Oxlint, tsrs typecheck, Bun unit/CLI tests.                                                                                     |
| Installer and provisioning | `python3 -B -m unittest discover -s platform -p 'test_*.py'`                                             | Disk selection/confirmation guards, configuration schema, digest and archive handling, activation/recovery fixtures. Not a substitute for an installed guest.       |
| Runtime                    | `bash runtime/tests/runtime-config.sh`; `python3 -B runtime/tests/browser-config.py`                     | Staged units, effective OpenSSH forwarding restrictions when sshd is available, local job/WayVNC rejection paths and browser-fixture boundaries.                    |
| Agent                      | `python3 -B -m unittest discover -s runtime/tests -p 'test_*.py'`                                        | Wrong artifacts, traversal, conflicting settings and changed installs fail; identical fresh registration is repeatable. Offline fixture does not launch a provider. |
| Graphics                   | [Guest acceptance matrix](../runtime/README.md#optional-persistent-virtual-desktop-validation-candidate) | Native Wayland and XWayland screenshot/input/accessibility/reconnect require the actual driver and compositor. The certified matrix is empty.                       |

The published HolyAgent 0.3.3 tarball was independently fetched, verified and staged twice in a new HOME; its contained Bun launcher returned `0.3.3`. A complete bundle with the compiled CLI, real HolyAgent package, Pi dependency tree and T3 Code native release passed offline build, hash verification and staging. The real T3 native executable accepted the managed policy; it returned HTTP 200 on loopback before and after an isolated restart, retaining the Pi driver settings and an uncommitted worktree marker. A credential-free Pi RPC session with bundled Node/Bun registered the headless tool suite and exercised native FFF lookup without submitting a model turn. The official installer ISO passed its SHA-256 and signature checks and booted through UEFI in a disposable, networkless QEMU guest under TCG. This observed boot is not a completed installation. Chromium could not start its sandbox in this environment; only its fixture/config tests passed. No credentials or provider were involved. These results do **not** certify T3 + Pi end-to-end operation, Podman cgroup limits, graphics, a live tailnet, real hardware, or a full QEMU install/reboot. Record those separately with guest versions and observed results.

Before using a guest for real work, verify reboot to multi-user.target, correct service identities, persistence of a disposable worktree, and the actual bind interfaces. Exercise interruption/retry, previous-release selection and graceful rejection of an unknown artifact. From an independent authorized node, test tailnet denials and positive forwarding, verify host keys and retain a working console until finished. For GUI qualification use non-sensitive local fixtures and a separate guest; an open VNC port does not prove CUA works.

## Opt-in installed-guest gate

The **Disposable guest acceptance** workflow is separate from normal CI. For a same-repository PR, add the literal `<!-- run-t1os-vm -->` to its description; only the edit that adds the marker opts in. To retry, remove it and add it back. Once the workflow is on the default branch it can also be dispatched manually. It uses only a standard GitHub-hosted runner on a public repository: [GitHub documents this as free](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) and [documents Linux hardware acceleration](https://github.blog/changelog/2024-04-02-github-actions-hardware-accelerated-android-virtualization-now-available/). It checks actual KVM availability and free disk space; either can block a run. It cannot use a larger paid runner, a personal computer or live credentials.

A successful run requires the stock installer to reboot, an offline appliance to validate the installed Omarchy root and stage the pinned overlay, and two subsequent boots from disk without either installer medium. The installed guest checks its boot target, operator privileges, inactive stock listeners, and real compiled CLI, and reopens the same operator-owned Git commit and checkpoint on the next boot. A QEMU splash, a green unit-test workflow, or a skipped acceptance job is not a pass. Each run discards its test VM; it does not deploy or distribute a VM image.
